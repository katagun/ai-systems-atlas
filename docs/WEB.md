# Web application

The `web/` directory is a dependency-free static application. `app-core.js` contains pure filtering, sorting, and ranking behavior plus the data tables they read; `app.js` owns browser state, the DOM, and rendering. The seam is injection, not a shared global: a helper that needs a taxonomy name or a stored value takes it as an argument (`searchFields(kind, record, { labelOf })`, `recommendationReasons(project, priority, labelOf)`), so the unit suite in `tests/test_web.js` can `require` the file and call it directly. Anything that reads `document`, `localStorage`, or `history` stays in `app.js` and is covered by the e2e suite instead. Markup-returning helpers are the known exception to the seam, because a string is not logic; `emblemSVG` and `badgeLettering` build SVG and badge text respectively.

## Visual language

The interface uses a technical editorial system: cool paper backgrounds, crisp white surfaces, teal, coral, and violet taxonomy accents, a subtle coordinate-grid texture, and restrained dimensional shadows. Bricolage Grotesque carries display hierarchy, IBM Plex Sans carries body text, and JetBrains Mono carries evidence, metadata, labels, and counts. The three faces are vendored into `web/fonts/` by `scripts/build_fonts.mjs`, which also writes `web/fonts.css`, so the published page makes no third-party request at runtime. New components must take every colour from the custom properties in `styles.css`: the light palette lives on `:root`, and the dark palette is defined twice, once under `@media (prefers-color-scheme: dark)` guarded as `:root:not([data-theme="light"])` and once under `:root[data-theme="dark"]`, so the OS preference and an explicit choice resolve the same way. `tests/test_web.js` fails the build when the two dark blocks differ or when a colour literal appears anywhere else in the file; derive tints with `color-mix()` from a token rather than adding a literal. Corner radii follow the same rule: `--radius` rounds containers such as cards, panels, tiles, and dialogs, `--radius-control` rounds inputs, buttons, and other controls, `--radius-chip` rounds badges, tags, and marks, and `--radius-pill` rounds pills and dots such as the Finder's priority pills, tile categories, strip entries, and state dots, and the same test fails on any `border-radius` literal outside `:root`. The primary navigation is plain text with a two-pixel underline under the active view at every width, so the pressed entry of the results strip below it is the only filled control of its kind on the page. The footer opens with a compact site map and the Suggest a system action, then a two-zone grid on the content column: the notices stack left at a reading measure and the data date sits right in the mono metadata voice, collapsing to one left-aligned column on a phone. Preserve strong contrast and information density in both palettes, and keep decoration subordinate to taxonomy and evidence. Directory cards lead with a small product mark — a monochrome logo vendored into `web/logos.json`, or a monogram fallback — rendered in `currentColor` so marks stay subordinate to the taxonomy accents.

## Mobile landing and navigation

Below 768px the app uses the Elements-first mobile layout from ADR 046: one family at a time, with Agents leading the family buttons and shown until a restored role reveals its own family, compact collection tiles, and a fixed Home / Search / Finder / Explore / More bar. Search focuses the existing mixed catalog; Finder replaces the landing job shortcuts. More owns documentation links and the existing theme/GitHub controls, moving the controls back to the header at desktop widths. Reference-sheet restoration reveals the selected family, and a family switch closes an incompatible sheet. The bar reserves safe-area space and stacks below the badge legend and comparison tray; a keyboard-sized visual viewport reduction while editing hides it. Desktop and the static blog keep their existing header. Browser coverage is in `tests/e2e/mobile-landing.spec.js`.

## Content hierarchy

The directory landing view is action-first. Keep its always-visible introduction to one short value proposition, one supporting sentence, and the first Finder job of each direction. Its All scope presents every record the site publishes — systems, the complete models.dev source catalog with reviewed overlays, inference services, local runtimes, agent packs, robots, labs, and specifications — without merging their canonical records or scores. That is the whole of it: the scope is named for holding everything, so its count is the total of every collection's payload rather than a figure maintained beside them, and a collection added later is in the scope without a second edit.

Use progressive disclosure for explanation and specialist controls:

- The Directory opens on the front door: the headline, one supporting sentence, one search across every collection, the first Finder job of each direction as a link, a stage, and the index, one tile per collection from `AppCore.COLLECTIONS`. The stage has three faces, Elements, Models, and Systems, chosen with the same underline as the primary tabs and never advancing on its own. Elements is the role map. Models and Systems each lead with the newest reviewed record and then list the rest newest first, a shared date broken by name; a model uses its release date and a system uses its review date, because a system has no release date. The collection index stays visible on every face. A tile carries the collection's emblem (its first type badge; three connected modules for Systems, the agent head for Agent packs, the type family's empty frame for Everything, an articulated robot arm for Robots), the count its default view lists with its split (Models: reviewed and imported; Agent packs: packs and host-installed systems; Systems: active), its largest categories as links that open the scope narrowed to one, the three records reviewed most recently as marks (ties by name), and a dot when a comparison is in progress there or the Finder's role set is applied. Tiles carry no definitions. An empty collection has no tile.
- Elements groups active systems by their taxonomy-defined family and primary role, with a count and a display symbol per role. It is navigation, not a periodic law or a ranking. Selecting a role opens an inline reference sheet with an alphabetical record selector, recorded properties, editorial review date, limitations, and links to its exact catalog slice and full evidence dialog. Tiles preview the organizations that build their systems rather than the systems themselves: the labs owning at least one of the role's systems, in the reviewed `display_order` then by name, three of them on desktop and two on phones with a remainder count and a tooltip naming the rest (ADR 049). A lab with no mark is left out rather than shown as a monogram, and a role no lab owns carries no strip at all, so a tile never shows a placeholder where a logo would be. The selected reference record keeps its own system mark. Previews reuse the deferred logo loader, which decides the membership, so a tile reserves the strip's height until it arrives. Counts use boot data; review details load only on selection, with a retry on failure. No cross-family scores appear. `element` and `elementRecord` restore the sheet on reload and Back; leaving for results or another view removes them. On phones the sheet follows its family, and closing returns focus to its role tile. See [ADR 046](adr/046-elements-adds-role-navigation-and-reference-sheets.md).
- Choosing a tile opens results; the Everything tile is the A–Z list (`collection=all`). Every tile, Models, Labs, and Specifications included, opens its Catalog collection; legacy `?view=models|labs|specifications` URLs alias to the same collection. Typing on the front door searches everything and lands in results with the caret in the results search.
- In results a sticky strip under the header lists every collection from the same registry, emblem, name, and count, with exactly one pressed (`aria-pressed`); Systems uses three connected modules to represent the collection spanning memory, agents, and assistants; Robots uses an articulated arm. Each uses the same emblem as its front-door tile, at every width. These are collection navigation marks, not family or form-factor claims or card badges. From 1001px to 1407px each entry shows its short name (Services, Runtimes, Specs), so the row stays one row and the strip at most 96px tall inside Systems; the full name stays the accessible name, and full names show from 1408px, where the content column reaches its cap. Focus and anchor scrolling stop below the sticky header and strip: `app.js` measures their height into `--sticky-clearance`, which `html`'s `scroll-padding-top` reads. At 1000px and below the entries are emblems only, the pressed entry's name and count read as a caption under the one row, and the row never scrolls sideways (nine entries fit 320px with at least 16px measured slack); the header remains a single sticky row at every width, with the strip directly beneath it. Inside Systems a second row lists All families, Memory, Agents, and Assistants with active counts, one pressed; the Systems entry clears the family, role, Finder roles, and comparison. A coral dot marks a comparison in progress in that collection, a violet dot the Finder's role set applied to Systems.
- In results a bar directly under the strip holds one search box, `#results-search`, for every collection, and the Sort control of a collection that has one. Above 1000px it sticks under the strip and `--sticky-clearance` counts it; at 1000px and below it scrolls with the page. While a query is present, every strip entry, the pressed entry's caption, and the Systems family row count the query's matches in their default view, updated in place rather than rebuilt, and each entry's accessible name says so ("Labs 3 matches"). A query made only of common words, such as "the" or "me", counts as browsing, as the results already treat it. At 1000px and below the entries' counts are visually hidden, never removed, and at 720px and below so are the unpressed family entries' counts. The front door's heading needs a top margin that results do not, so the results drop it.
- In All, expose one shared search, list alphabetically while browsing and by match while searching ([ADR 040](adr/040-search-orders-by-match-never-by-score.md)), and hide numeric scores.
- In Systems, keep Search, Family, Role, and Sort visible; keep source model, license, agent relation, architecture, deployment, interface, capability, status, and local-first under “More filters.”
- In Inference services, keep search, service type, delivery, model source, API style, and score sort visible.
- In Local runtimes, keep search, runtime type, accelerator, model format, API style, and score sort visible.
- In Agent packs, keep search, pack type, host, install mechanism, and licence visible; results are alphabetical while browsing and ordered by match while searching, and unscored.
- The Packs grid lists packs and scored systems whose deployment includes `host_pack` inline, alphabetical by name while browsing and ordered by match while searching; pack facets narrow only packs while the search term narrows both; scores stay hidden, nothing offers comparison, and each system card opens its own system dialog (ADR 035).
- In Robots, keep search, form, AI, availability, and status visible; results are alphabetical while browsing and ordered by match while searching, unscored, and never offer comparison.
- In Models, keep search, model type, distribution, modality, source model, license, and the sort (best match, access score, release date, or name) visible, and a Lab filter that narrows to one lab's releases.
- In Labs, keep search, type, headquarters, and release distribution visible; results are alphabetical while browsing and ordered by match while searching, and unscored.
- State the applicable score-scope rule in each collection's scope note, the line under its result count. Models, Labs, and Specifications carry their counts there too (`#models-kicker`, `#labs-kicker`, `#specifications-kicker`).
- Offer comparison only after the user enters one comparable scope: a selected system family, Inference services, Local runtimes, or Models.
- Put definitions and classification rationale in Taxonomy.
- Put the published JSON files, their fetching and licence terms, and what is deliberately unpublished in API. It is the human counterpart to `web/llms.txt`; keep the two saying the same thing.
- Put evidence, score dimensions, strengths, and weaknesses in project details.
- Keep Specifications as a Catalog collection with direct filters; show contract boundaries and evidence only on demand.
- Keep inference-service constraints, score dimensions, terms, and evidence in its record-specific detail dialog even though discovery shares the Directory surface.
- Keep local-runtime execution traits, hardware requirements, score dimensions, licensing, and evidence in its record-specific detail dialog.
- Keep Labs as a Catalog collection. A lab card and dialog show what the catalog already holds about the organization, joined by name in the browser; the lab record itself adds only who the organization is, where it publishes, and the framework it publishes ([ADR 041](adr/041-labs-are-unscored-records-of-who-develops-the-catalogs-models.md)).
- Keep Models as a Catalog specialist collection while also including every models.dev source record in mixed Directory discovery. Overlay reviewed records by `source_id`, or by `id` for a reviewed record with no `source_id` yet; imported cards and details must say they are not Atlas reviewed, while reviewed details show boundary, licensing, score dimensions, and evidence.

Prefer plain interface labels over methodology language. Use exact taxonomy terms when changing their meaning would introduce ambiguity, but do not repeat the taxonomy thesis on the front door, in filters, or in the footer.

### Card badges

The [2026-09-29 badge review](BADGE_REVIEW_2026-09-29.md) evaluates OSS and API-compatibility proposals and records implementation gaps. The six follow-ups are implemented under [ADR 047](adr/047-badges-identify-record-facts-and-licensing-stays-scoped-text.md); the dated review preserves the original findings.

Every published card carries at least one badge. Badges are defined once in `CARD_BADGES` and listed per collection and system family, in priority order, in `CARD_BADGE_SETS` in `web/app-core.js`. The design budget is six: one type badge plus at most five traits. Registry and published-data tests enforce it; the renderer preserves every match and wraps rather than silently truncating if future data exceeds the budget. On system, inference-service, and local-runtime cards the badges replace the tags row, and on reviewed-model cards they replace the role pill. Badges are for scanning only: they never carry merit, editorial picks, trust or evidence state, or automated signals such as stars, and they never rank.

Each card leads with exactly one **type badge**, which says what kind of record the card is. It tests the one field that classifies the record in its collection for a single value: `system_family`, `service_type`, `runtime_type`, `model_type`, `specification_type`, `pack_type`, `lab_type`, or robot `form_factor`. For an imported models.dev row it tests the imported status, and the badge is named Source record. Every value of each of those vocabularies has a type badge, whether or not a published record carries it yet, so a new taxonomy value cannot ship without one. A type badge is the one deliberate restatement on a card: it repeats, as an emblem, the type the eyebrow prints, so every emblem row starts with the record's kind. It is exempt from the separation guideline below because it identifies rather than filters. Specifications, agent packs, labs, robots, and imported models.dev rows carry their type badge and nothing else; reviewed models carry their type badge and distribution badges. Robot glyphs cover every form factor and say nothing about AI capability ([ADR 047](adr/047-badges-identify-record-facts-and-licensing-stays-scoped-text.md)).

Every other badge is a **trait badge**. Each tests one reviewed field for presence — a boolean that is `true`, or an array that contains a named value — so a missing trait badge claims nothing is absent. A trait badge never repeats a fact its card already prints: role pills show API styles on services and runtimes, and service footers show model sources, so no trait badge tests those fields. A reviewed-model card has no role pill; its distribution modes print only as badges, so every mode is a badge, including Developer API at about 77% of reviewed models, and every reviewed model carries at least one. Share a badge name across system families only when it tests the same field and value. Add a badge only when it separates cards, roughly 10–75% of its collection or family; values nearly every record carries are noise. Specifications, imported models.dev rows, and labs carry no trait badges. The first two have no reviewed trait to test. A lab's distribution modes are joined from its releases rather than reviewed on the lab, so they print as one plain label. A reviewed-model card keeps its models.dev modality and family as plain text attributed in a `title` and in visually hidden text, and no badge tests `source_metadata`. A card whose record has no recognised type value and no trait omits the row; no published record does. `robot_control` has no badge: it separates about 2% of agent systems, below the floor, and the agent set already holds six badges; the Capability filter and the record's Agent operation block carry it instead ([ADR 045](adr/045-robot-software-classifies-by-the-outcome-it-owns.md)).

Badges render as icon-only emblems rather than text chips. Each badge has exactly one `family` in `BADGE_FAMILIES` in `web/app-core.js`: Type (a circle frame in the neutral `--slate-ink`, so the kind reads apart from the coloured traits), Control and privacy (a shield frame, `--cyan`), Capabilities (a hexagon frame, `--violet`), and Platform and hardware (a rounded-square frame, `--amber`). The family decides the emblem's frame shape and accent colour; `styles.css` colours a family's emblems through its `[data-family]` selector rather than a literal. One glyph maps to exactly one badge id: glyphs are hand-drawn 1.5-unit strokes on a shared 32-unit viewBox (the Agent system mark is an angular robot head with a sensor visor and side actuators), and the three accelerator badges are lettered `MTL`, `ROC`, and `NPU` instead of being drawn or borrowed from a vendor mark. MCP is the exception: it uses the [official MCP logo](https://github.com/modelcontextprotocol/docs/blob/573dc60c2e7aab2605b29d0bf27194aa7b02e4fb/favicon.svg), with its paths and stroke proportions preserved and scaled uniformly inside the capability frame; its MIT notice is in `third_party/mcp-logo-LICENSE.txt`. Cards, Finder, the legend, and Taxonomy all render the same badge definition.

Individual emblems are not controls and take no tab stop. Each card and Finder badge group has one native “Badge meanings” disclosure, keyboard-operable with Enter or Space, showing the same names and definitions beside the record. Each still carries its name and definition in visually hidden text beside the emblem, so a screen reader announces it once. One shared tooltip, `#badge-tooltip`, is `aria-hidden` and pointer-only: it shows the badge's family, name, and definition, opens on hover and on tap, and closes on Escape, on scroll, on an outside tap, or when the pointer leaves the combined trigger, gap, and tooltip region. Tooltip text itself accepts pointer hover, so readers can move to and select it without dismissal. Once Escape closes it, it stays closed until the pointer moves, so a repaint or a scroll under a resting pointer never brings it back. There is no `title` attribute on a badge. Emblems sit above the card's own click target, so a tap on an emblem opens only its tooltip.

A legend strip fixed to the bottom of the viewport names the active scope's emblems, type badges first:

- in the Directory's Systems scope, the union of badges across families, narrowed to one family's set when the Family filter picks one;
- in All and Agent packs, only the four families, not individual badges;
- in Models, the model types, the Source record badge, and the distribution badges;
- in Specifications, Labs, and Robots, the view's type badges;
- in Finder, Taxonomy, and API, nothing. Finder shortlist cards carry badges, and their tooltips explain them. `badgeLegend()` in `web/app-core.js` decides the contents for a given collection and system family. The strip stays one row tall at every scope and viewport width: the emblem list scrolls horizontally while the Key label, the All badges link, and the close button stay fixed. In All and Agent packs each family shows its emblem and name only, with its meaning kept as a hover title; full meanings live in Taxonomy. The legend collapses to a small "Key" chip, remembers the reader's open-or-closed choice in `localStorage` under `atlas.badgeLegend`, and starts collapsed by default under a 720px viewport when no choice is stored. The legend and its Key chip both step aside while the comparison tray is open, since the tray owns the same edge of the viewport, and return as the stored choice says once the comparison is cleared. The page measures the strip: while the strip is open, keyboard focus and scrolling keep content clear of it, and the page footer ends above it rather than under it. Closing the strip moves focus to the Key chip, and reopening it moves focus to its close button.

The Taxonomy view separately explains navigation symbols from `COLLECTIONS.meaning`, using the same artwork and labels as tiles and the strip. It lists record badges in one group per family, headed "Card badges · <family name>", stating the family's meaning and showing every badge in that family with its emblem, name, and definition.

A triangle emblem frame is reserved for a possible future tier of reviewed flags, such as marking cyber-capable systems or systems with advanced, dangerous capabilities. Flags would be editorial judgments rather than presence tests, so they need a reviewed field, an evidence bar, and an ADR amending this contract before any data or UI work begins; the reservation is only a spare frame shape, not a commitment to build it.

Licensing remains text, not an OSS trait. Model surfaces use `source_models[].model_name` and `model_definition` for artifact-scoped wording; systems and runtimes use the software-scoped `name` and `definition`. See [Models](MODELS.md#artifact-licensing-labels). Evidence-review attention remains separate from badges and appears consistently on scoped system cards, mixed system cards, and Finder.

Run `node scripts/report_badges.mjs` for a non-blocking prevalence report with denominators (canonical published records, including archived; imported model rows excluded) and explicit distribution-mode exceptions.

Cards paint from the boot payload, so any field a badge tests must be in `BOOT_FIELDS` in `scripts/build_web_payload.py`. Tests compare canonical and boot badge IDs/order and predicate values, not just field presence. When the data guard in `tests/test_web.js` reports that a badge no longer appears on any card where it is listed, remove the badge from that list or re-justify it against the 10–75% guide; never change a record to satisfy the guard.

## Behavioral contracts

- The default Directory scope shows every reviewed system, every models.dev source record with reviewed releases overlaid, every inference service, every local runtime, every agent pack, and every robot alphabetically, including archived system references, with scores hidden across collections. A query lists only its matches, ordered by match.
- Mixed Directory search indexes visible identity, editorial, and boundary prose rather than hidden provider metadata or evidence URLs.
- Collection controls are mutually exclusive, expose their selected state accessibly, and preserve the selected collection (`all`, Systems, Inference services, Local runtimes, Agent packs, Robots, Models, Labs, or Specifications) in the `collection` URL parameter. Exactly one strip entry is pressed, the collection shown; inside Systems exactly one family entry is also pressed, All families included, while Systems stays pressed above it.
- The Systems scope defaults to every active memory, agent, and assistant family alphabetically, with cross-family scores hidden. A query selects Best match.
- Search matches words, not substrings ([ADR 040](adr/040-search-orders-by-match-never-by-score.md)). Every query word must match. Case and accents never matter. Hyphens split query words, so `self-hosted` and `self hosted` ask the same thing, and a period that ends a query word is dropped, so `ollama.` asks for `ollama` while `.net` and `llama.cpp` stay whole. A record's word joined by `.`, `+`, `#`, or `-` also counts as its parts, so `llama` finds `llama.cpp`. The stop words `a`, `an`, `the`, `for`, `with`, `my`, `to`, `of`, `and`, `on`, `in`, `i`, and `me` are dropped. Each query word matches as typed or as its light stem, whichever matches better. In a word of five or more letters, the stem turns a final -ies into -y. Otherwise it drops a final -s, but not -ss, from a word of five or more letters, then -ly, -ing, or -ed when four letters remain. So `agents` finds `agent`, `memories` finds `memory`, and `series` still finds `series`. Words of four or more letters match the start of any word, and anywhere inside a word of the record's name. Three-letter words match a whole word or anywhere inside a name word. Two-letter words match a whole word or the start of a name word, and one letter matches the start of a name word, in every collection. So `Pi` never matches `API`, `rag` never matches `storage` in prose, and `gpt` finds ChatGPT.
- A short reviewed synonym list (`SEARCH_SYNONYMS` in `web/app-core.js`) replaces whole query words with the catalog words that answer them, so `note taking` asks for `notes`, `chatbot` for `chat`, `sso` for `single sign on`, and `k8s` for `kubernetes`. A record matches on its best variant, and every entry is pinned by a real-catalog probe in `tests/test_web.js`.
- While searching, results are ordered by match: always in All, Agent packs, Specifications, Labs, and Robots, and under Best match in the scopes with a Sort control. That order never reads a score, stars, or any other merit, and browsing keeps each scope's own order. A name that holds every query word counts most, then the record's label, then its maker, then its description, then its other searchable prose. A query of two or more words also earns a phrase bonus, in the same proportion, from the heaviest field other than the name that holds its words one after another in order. Each word matches there by the rules above, and stop words are skipped on both sides. So `self hosted`, `self host`, and `the self hosted` all list records described as self-hosted before services whose type name only says "host". A phrase in a label still counts less than a name that holds every query word. The label is the record's role or type name from the taxonomy (for a robot, its form factor), and for a system also its family and source-model names. The maker is the record's repository when it has one, and otherwise the operator, maintainer, developer, steward, or manufacturer it names. A name or short name equal to the query as typed, stop words included, comes first, so `A-MEM` lists A-MEM first and `ACP` lists Agent Client Protocol first; then come names that start with the query, then names that hold every query word. A split name counts as one: each pair of neighbouring query words is also tried as one word, so `lang chain` lists LangChain first. The joined word counts where a name holds it by the name rules, or where any field holds it as a whole word. A field holding it whole earns the phrase bonus by its weight, the name included. So `lang chain agents` still lists LangChain first, and `lang chain` lists LangGraph, whose repository holds `langchain`, ahead of models that only say "language" and "chain-of-thought". Among equal matches, active records come first, then names A–Z; a record is active unless its status is archived, superseded, or removed, the statuses the taxonomy defines for a record that is no longer current. The match weight is computed in the browser, never published, and never shown on a card.
- Systems, Inference services, Local runtimes, and Models list "Best match" first in their Sort control, and offer it only while a query is present: while browsing it is disabled, and a link that names it without a query loses it on restore. A query selects it unless the reader chooses another sort during that query, and a sort chosen then survives further typing. Clearing the query restores the sort from before it, unless the reader chose one during the query, which stays. Clear filters and the Finder's handoff clear the query and set the sort themselves, so the next query selects Best match again. While a query is present, Best match is the sort's URL default and is never written, and a sort the reader chose during the query is written even when it is the browsing default, so a reload keeps it. A link with a query and no `sort` opens on Best match, and a `sort` the link names counts as chosen.
- One search box, `#results-search`, serves every Directory collection, the family entries included, so a query follows the reader by construction. A change to its text returns every collection to its first page. Typing on continues the same query, so a sort the reader chose during it survives in that collection until the query is cleared, and each collection keeps its own sort from before the query. The results, the strip's counts, and the URL follow 150ms after the last keystroke, and the results region is `aria-busy` until they have; the sort follows at once. The Finder's handoff, "Browse all in Models", and every Clear control clear the query.
- "/" focuses the visible search box unless focus is already in a field, and does nothing in Finder, Taxonomy, or API, or while a dialog is open. The results search shows the collection's result count ("12 results") beside the input while it holds a query. That count is `aria-hidden`; the result row's live count is the one a screen reader hears.
- When a search lists nothing, the result spans the grid at a readable measure and says what the reader can do next. Its heading is "No matches for “X”.", or "No matches for “X” with these filters." when the scope's filters hide matches. An empty result first loads every collection's search index, and until each one has landed or failed it offers only did-you-mean and the Finder, so no count, exclusion, or suggestion below rests on part of the catalog. Below the heading, in order:
  - "It matches N reviewed records your filters hide." with "Show it" or "Show them", when the scope's own records match but its filters hide them. The button clears every filter the scope's URL carries except the query and the sort, and in Systems also a Finder role set, then returns focus to the search box. "Reviewed" appears only when every hidden match is a reviewed record, so a hidden imported models.dev row is not called reviewed.
  - "It matches records in other collections:", followed by one button per collection whose default view lists matches ("Labs 3"), which opens that collection with the query, and "Search all" when All lists matches this collection does not. All's own empty result names Labs and Specifications, which All leaves out. Each button focuses the results search.
  - "Did you mean …?", offering up to three record names that are, whole or by one of their words, within one edit of a query of three to seven characters, or two edits of a longer one. The names come only from the records the scope lists under its current filters, never repeat the query, and replace the query when chosen.
  - "Reviewed and left out:" with the entry's name and reason, when the query is an `exclusions.json` entry's name, ignoring case and accents and reading a hyphen as a space, so `claude squad` names `claude-squad`.
  - "Try the Finder", always.
  - "Suggest it for review", only when nothing in any collection matches, with every filter ignored, and no `exclusions.json` entry names the query, so it also waits until that list has loaded or failed. Those collections are systems, models, inference services, local runtimes, agent packs, robots, labs, and specifications. It is a link to the GitHub suggestion form with its Name field filled in, so the page itself makes no request to GitHub.
- When a query names a Finder goal, a banner above the All, Systems, Inference services, and Local runtimes results says "Looks like a job: <goal>. The Finder can shortlist from N reviewed records." and offers "Open shortlist →", which opens the Finder with that goal chosen and its shortlist already ranked. A goal may carry reviewed `keywords` that count as its label when a one-word query names a goal (`sql`, `retrieval`, `gateway`), and a synonym variant retries naming when the typed query names none. A query names a goal when at least 60% of its words of three or more letters, and at least one, match words of the goal's label or description, and the goal has eligible records. A query with only one such word names a goal only when that goal's label holds the word and no other goal with eligible records holds it at all. So `browser` names "Operate websites or browsers", while `agent`, `model`, `rag`, and `sql` name none: the first two appear in several goals, and the last two only in a description. ## Explore

`?view=explore` opens the model-access overview, runtime feature matrix, and system-deployment analysis from the catalog introduction, Docs menu, or footer (including the blog shell). Explore uses the same content width and gutters as the landing page, without a narrower view-specific cap. Distribution bars count releases carrying each mode, with all reviewed releases as denominator. The semantic license-classification table uses each row's release count as denominator. Modes overlap: a release counts once in every mode it carries, regardless of the number of licenses. Unknown classifications get a visible row, and missing distribution modes stay in the denominators with an explanatory notice. Empty reviewed data gets an empty state. The page names the reviewed count, excluded imported count, and model collection review date; it claims neither market share nor model quality.

Nonzero bars and classified table cells are ordinary links to the existing Models distribution and source-model filters, sorted by name. They create a navigation history entry so Back returns to Explore; zero and unclassified cells have no misleading drill-down. No scores or comparison controls appear in Explore. All labels come from taxonomy and every dynamic text or URL is escaped. Shared theme tokens cover the bars and table in both palettes.

The runtime matrix lists runtimes alphabetically, with combined accelerator and format filters. The suite starts its own server on a port derived from the checkout's path and never adopts one it did not start, so the exploratory server below and a suite running in another worktree cannot serve it another checkout's `web/`.
