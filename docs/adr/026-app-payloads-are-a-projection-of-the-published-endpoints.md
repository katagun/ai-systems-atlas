# ADR 026: App payloads are a projection of the published endpoints

**Status:** Accepted

## Context

The nine catalog files under `web/` — `projects.json`, `taxonomy.json`, `exclusions.json`, `license-evidence.json`, `specifications.json`, `inference-services.json`, `local-runtimes.json`, `models.json`, and the MIT-attributed `models-dev.json` source snapshot — are a public API. They are documented in the API view, listed in `web/llms.txt`, and fetched by parties this project cannot see: the endpoint list promises a shape and a caching contract (a ten-minute `cache-control` and an `ETag`), not a shape that happens to suit today's page.

Those same files were also what the web app downloaded before it could render a single card. That is the tension: the record a reader clicks into needs `strengths`, `watchouts`, and prose evidence, but the grid a reader browses first needs none of that. A verification pass measured `projects.json` and found that 64% of its bytes are prose that renders only after a click — description, strengths, watchouts, and evidence detail, none of it visible on the card. The boot payload before this project's earlier work was 252.0 KB gzipped; two already-committed changes brought it to 182.8 KB. Minifying `web/*.json` in place was tried and measured: it saves only 9.0 KB gzipped (3.3%), because gzip already collapses indentation and whitespace, so reshaping the whitespace is not where the remaining cost lives — the remaining cost is in shipping detail fields the boot render never touches.

One artifact cannot serve both purposes at once. A public contract that agents and third-party consumers depend on must hold its shape so a documented cache policy and a stable schema stay meaningful. A payload tuned to how the page loads today must be free to change the moment the page's rendering strategy changes — moving a field onto the card, splitting the boot request further, adding a field the detail dialog needs. Pinning the published schema to whatever the app currently renders would mean either the contract drifts on every UI change, or the UI's paint cost is permanently held down by contract stability that has nothing to do with reading a record.

## Decision

The endpoints are the contract and never change shape for the app's convenience. `directory/*.json`, synchronized byte-for-byte into `web/*.json` and validated by `validate_published_copies` (`scripts/validate_directory.py:1214`) against the `PUBLISHED_DATA` tuple (`scripts/validate_directory.py:18`), keeps documenting the full record for every reader of the public API, human or automated.

The app instead reads a generated projection under `web/app/`, regenerated from the published endpoints by `scripts/build_web_payload.py`. The Models projection overlays `models.json` reviews on `models-dev.json` source rows by `source_id`; every source row appears once and carries an explicit review status. This projection carries no compatibility promise: it may be restructured, split, or dropped in any change that touches how the page loads, without deprecation notice. It is never advertised in `web/llms.txt`, never described in the Atlas skill, and never added to `PUBLISHED_DATA` or the API view's endpoint list. It is an implementation detail of the page, not another published catalog endpoint.

## Consequences

Payload shape under `web/app/` may change with any web change and needs no deprecation period, no version bump, and no entry in the endpoint documentation — it answers to the app's rendering code, not to external consumers. The projection must be regenerated by `scripts/build_web_payload.py` wherever `web/` is synchronized, or the app ships a stale boot payload beside a current published record; this is why the Commands block in `AGENTS.md` lists the build step immediately after `sync_web_data.py`. `web/app/` is committed rather than built at deploy time, because `deploy-pages.yml` uploads the contents of `web/` directly with no build step in between. Agents and API consumers use the separately documented endpoint schemas, while the byte-for-byte synchronization check protects each public contract.

## Why the complement rule

The projection's reviewed-record detail shape is defined as the published record minus the boot fields — a complement, not a hand-picked include-list. A curated drop-list was considered and rejected. An earlier pass proposed dropping nine fields from `projects.json` that no known view renders. `BACKLOG.md` separately asks to "Render `current_repo_note`, or decide it is not reader-facing," about a field that carries product-boundary prose `docs/CURATION.md` requires reviewers to write — the note distinguishing a vendor's assistant, coding agent, and platform records from one another, load-bearing editorial content that today reaches no reader only because nothing renders it yet. A field that is unrendered today is not evidence that it should stay unrendered; it may be evidence of a rendering gap the backlog already intends to close. A curated drop-list has to guess right about every field, forever, and a wrong guess silently deletes a record's meaning from the app's payload the next time it regenerates. A complement rule cannot make that mistake: whatever the boot view does not explicitly claim stays in the detail projection, so closing the backlog item changes what renders `current_repo_note`, not what the payload carries. Imported models.dev source rows are the deliberate exception: compact card and filter fields remain in the Models boot payload, while their shared source-only dialog fields live in one lazy `app/model-source-details.json` payload rather than hundreds of per-record files.
